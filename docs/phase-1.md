# Phase 1 — Parquet vertical slice

Phase 1 delivers a **real local scan pipeline** for Parquet-first workloads: resolve targets,
enumerate files with caps, classify formats, read Parquet footers, infer a logical dataset,
run a first rule pass with **namespaced finding codes**, and emit a **validated
`ScanReport`**.

> **Note:** Phase 2 generalizes this to **`ScanEngine::run`**, multi-dataset grouping, shallow
> text probes, and structured Parquet failures — see `docs/phase-2.md`.

## What works end-to-end

- **Local file and directory targets** via `resolve_local_scan_plan` and `ScanEngine::scan` (historically `LocalScanEngine`).
- **Extension-based format detection** for Parquet, CSV, JSON/NDJSON hints, and unknown.
- **Parquet footer inspection** (schema leaf columns, row counts, row-group sizes, `created_by`).
- **Hive-style partition segments** parsed from path components relative to the scan root.
- **Logical dataset inference** (Phase 1 heuristic: one Parquet dataset per scan root).
- **Rule pass** emitting the required Phase 1 findings (see below).
- **Report validation** using existing `validate_report` invariants.

## Contract changes (0.2.x)

- **`FindingCode`** is now a **validated string newtype** with namespaces:
  - `system.<domain>.<name>[...]`
  - `plugin.<plugin_id>.<name>[...]`
  - `user.<name>[...]`
- **`Finding.detail`** replaces the old `explanation` field on serialized findings.
- **`Evidence`** now carries `summary`, optional `location_ref`, optional structured `payload`,
  and optional `references`.
- **Fingerprints** use **`V2CanonicalSortedJsonSha256`**: key-sorted JSON over a defined subset
  of finding fields (see `paraclete-types::fingerprint`).
- **`ScanPlan`** models resolved physical assets before deep inspection.
- **`CONTRACT_SCHEMA_VERSION` / `REPORT_FORMAT_VERSION`** bumped to **0.2.0**.

### Report versioning policy (product contract)

| Change kind | Version bump | Examples |
|-------------|--------------|----------|
| Additive JSON fields on reports or non-breaking optional objects | **Minor** | New summary counters, optional metadata map entries |
| Breaking shape or semantic rename on stable fields | **Major** | Renaming `detail`, removing required fields |
| New finding codes or categories without changing meaning of existing codes | **Minor** usually | Adding `system.quality.*` |
| Changing severity semantics for an existing code | **Major** if consumers rely on it | Redefining what “high” means for the same code |

## Intentionally deferred (Phase 2+)

- HTTP, CLI, TUI, CI/CD
- Object stores, logical dataset catalog resolution
- Plugin execution hosts
- Deep CSV/JSON/NDJSON inspection and sampling
- Row-level statistics, persistence, scheduling
